## 2.1 Модель — сделано

- `llm.complete(prompt, schema)`: `POST {LLM_BASE_URL}/chat/completions`, `response_format` json_object (схема в system) или json_schema (strict). Таймаут, 1 повтор на таймаут/сеть/429/5xx, 4xx — сразу ошибка. Ответ проверяется по схеме; пропущенные nullable-поля дополняются null, лишние отбрасываются. Ошибка → `summary` диалога, как раньше.
- `negotiate` / `learn_rule` — сигнатуры не менялись.
- `llm_proxy.py` — локальный OpenAI-совместимый эндпоинт: `codex` (Codex CLI) или `mock`.
- Осталось: прогнать 15–20 реальных диалогов на 2–3 моделях (YandexGPT Pro, Qwen в AI Studio, DeepSeek), критерии — не выдумывает факты, верно ставит ready/declined, цена.

## 2.3 Статус машины

- `trucks.status` free/busy (миграция `alter table`).
- `monitor()`: `active=1 and (status='free' or free_from <= today+2)`.
- PATCH диалога в `taken` → машина busy, `city_name` = город выгрузки, `free_from` = дата выгрузки или погрузка + дни пути (дистанция / ~500 км в день).
- Фоновая задача: `free_from <= today` → free.
- UI: переключатель «свободна/занята» на карточке машины.

## 2.5 Логины и роли

- `users(id, login, password_hash, role, active)`, роли owner / logist; argon2 (`argon2-cffi`); сессия в httpOnly cookie (подписанный токен, таблица `sessions`).
- Зависимость FastAPI на все `/api/*`, кроме `/api/login`; `/api/settings` (PUT) и `/api/users` — только owner.
- CLI `uv run python -m manage create-owner <login>`.
- Автор ручных действий (отказ, правило, «взяли груз», ручное сообщение) — в лог событий и в БД (`actions`).
- UI: страница логина, управление пользователями, скрыть настройки для logist.

## 2.4 Деплой

- Dockerfile (uv + собранный web), `docker-compose.yml`: app, caddy (HTTPS), voice (2.2), `restart: unless-stopped`.
- `DATA_DIR` для `data.db` и записей звонков → volume. SEED только при `DEMO_SEED=1`.
- Бэкап: ежедневно `sqlite3 .backup` + записи → S3-совместимое хранилище (Yandex Object Storage), 14 дней; одно восстановление руками.
- `.env` только на сервере.

## 2.2 Звонки (основная новая работа)

Спайк первого дня: может ли ВАТС МегаФон отдать голос боту.
- Основной путь: сотрудник-бот с SIP-аккаунтом в ВАТС; голосовой сервис на нашем VPS регистрируется как SIP-клиент; исходящий — командой API ВАТС от сотрудника-бота; события и записи — вебхуками ВАТС.
- Запасной: SIP-транк ВАТС напрямую в бота.
- Голос: Yandex SpeechKit (потоковое STT + TTS) → та же LLM; barge-in.
- После звонка: запись, расшифровка → сообщение `kind='call'` в переписке → `negotiate` обновляет facts/summary/status.
- Данные: `calls(...)`, `messages.kind`, `do_not_call`, kv: `call_enabled`, `call_after_min`=15, `call_hours`=09:00–19:00 МСК, `call_daily`. Один номер — не чаще 1 раза в 2 часа, не больше 2 попыток на груз.
- Телефон: берётся из `firm.contacts[].phones[]` выдачи ATI (проверено 12.11.2026). Если заказчик скрыт (нет `firm`), чат и звонок невозможны.
- UI: звонки в диалоге с плеером и расшифровкой, «Позвонить сейчас», страница настроек.
